① 系统全景：谁连谁

三个前端各自独立部署，共用同一套后端与同一套账号体系；后端只依赖 MySQL 与「可降级」的 Redis。

读图要点：虚线画的 Redis 意味着「它不参与正确性」——挂了业务照跑，只是更多请求会打到数据库。 这条设计贯穿全项目，也是抢单机制的关键（见 ⑤）。

② 一次请求的旅程：六道关卡

任何一个 /api/** 请求都会按这个顺序穿过六层，每层各管一件事。

最容易踩的坑：后端 HTTP 状态码永远是 200，成功与否写在 body 的 code 里。 所以前端必须在「成功分支」里判断 res.code === 200，否则你会拿到一个没有 data 的响应体却不报错。

三种协作模式： A 纯 CRUD Controller → 本域 Service → 本域 Mapper（计价规则、服务商档案）； B 跨域编排 本域 Service 借调其它域，一律注入对方 Mapper，只有 payment 注入 OrderService（为了复用带校验的查询）； C 框架切面 AuthInterceptor / MyMetaObjectHandler / GlobalExceptionHandler / OrderTimeoutTask，不出现在调用链里但每个请求都过。

④ 订单状态机：唯一合法的 8 条边

全部规则集中在 OrderStateMachine.TRANSITIONS 一张 EnumMap 里，order 与 payment 两个模块共用同一套校验。

为什么值钱：想禁止某条流转（比如「已接单不能取消」），只改这张 EnumMap 一行，所有调用方（下单、抢单、支付回调、定时任务）自动生效。 这也意味着改状态机时改这一处就够，不要在各种 Service 里散写 if-else。

⑤ 抢单并发：一条 SQL 决定谁赢 ★

三个司机同一毫秒点「立即接单」。Redis 只负责把 3 个请求压成 1 个；真正裁决胜负的是那条带完整 WHERE 的 UPDATE。

面试如果只让你讲一句话：把「共享资源独占给一个请求」做得最便宜、最可靠的方式，就是一条带完整 WHERE 的 UPDATE。 Redis、MQ 都是在这个基础上加性能，不是加正确性。

⑥ 抢单的 9 步（逐步做什么 / 为什么）

OrderServiceImpl.grab() 在一个事务里顺序执行，任一步抛异常则后续全部不执行、已执行的回滚。

1验司机资格
requireProvider + canAcceptOrder：启用 + 审核 + 在线 + 接单开关，四者全 1。否则 1006。
2Redis 短时防重
SETNX grab:{orderNo} TTL 5s。失败即 2003。只是削峰，不保证唯一。
3按单号查订单
前端传的是 orderNo 业务单号，须先查出 order.id 才能做条件更新。
4状态预判
必须仍是 PENDING_ACCEPT，否则快速失败，省掉后面开销。
5状态机校验
assertCanTransit(PENDING_ACCEPT → ACCEPTED)。第 4 步保护业务，这步保护状态图。
6服务范围校验
canServe：订单类型在 serviceTypes 内，且城市为空或相同。防止绕过大厅直调接口。
7条件更新（裁决）
grabOrder：WHERE status 且 provider_id IS NULL。影响 0 行 → 2003。唯一决定胜负的一步。
8写状态日志
insert order_status_log，operator_type=2。operatorName 反查昵称并落快照，用户改名不影响历史。
9finally 释放令牌
DEL grab:{orderNo}。注意这发生在事务提交之前，短窗口内会有请求进 DB，由 CAS 兜住。
看清"谁决定成败"：第 1、4、6 步是资格与范围（防不该抢的人抢），第 2 步是性能，只有第 7 步是并发正确性。 很多项目把第 2 步当成第 7 步用，那就是真的会超卖。

⑦ 支付与退款：两条独立的链路

支付成功由「支付模块反推订单」，退款由「管理端发起」。两条链路都用条件更新保证幂等，重复执行不会重复推进。

⑧ 三层防重：以「客户下单」为例

每一层都能独立生效，最后一层是数据库，永不失效。

第 1 层
前端
生成 X-Idempotency-Key 请求头 Home.vue 调 randomKey('order') 生成 order-<时间戳36进制>-<随机串>，同一次提交复用同一个 key
拦住了：用户手抖连点两次
▼
第 2 层
Redis
SETNX daijia:idem:order:create:{customerId}:{key}，TTL 5 分钟 命中即抛 5001「重复请求，请勿重复提交」。Redis 不可用时 RedisHelper 直接返回 true 放行（熔断 30s）
拦住了：同一 key 的并发重复请求
▼
第 3 层
数据库
orders.uk_order_no 唯一索引 + 捕获 DuplicateKeyException order_no 由「DO + 17 位时间戳 + 4 位随机数」生成，撞号概率极低，但撞了就转 5001，不会静默成功
拦住了：前两层全被绕过的情况
同样的三层结构也用在支付（幂等键 = 传入值 ?: 订单号，唯一索引 uk_idempotency_key）和退款（幂等键 = refund:{orderNo}:{refundNo}）上， 是项目里复用得最彻底的一个模式。

⑩ 已知缺口：按优先级

读懂了架构之后，能指出这些问题才说明真的读进去了。

优先级问题位置后果 / 修法
P0 抢单与大厅都没校验 expire_time，而定时关闭任务 60 秒才跑一次 grab() 第 261 行
pageHall 第 227 行		 中间最多 60 秒窗口能抢到本该关闭的单。
修：加 expire_time > NOW() 条件
P0 超时关闭是批量 UPDATE，不写 order_status_log OrdersMapper.closeExpiredOrders 时间线断档，客户看不出「为什么单没了」。
修：按 id 集合补写日志
P1 预约单的 expire_time 仍从下单时间算 create() 第 127 行 3 天后的预约单 15 分钟就被关。
修：改用 booking_time 倒推
P1 AuthInterceptor 每请求 3 次无缓存查询（用户/角色/权限） 第 80~100 行 抢单热点链路固定开销。
修：角色权限缓存进 Redis + 改角色时失效
P1 assignRoles 无事务：先删光再逐条插 SysUserServiceImpl:82-98 中途失败会让用户丢失全部角色。
修：加 @Transactional
P1 抢单失败错误码语义混淆（三种情况都是 2003） grab() 三处 「点了两次」和「被别人抢走」提示一样。
修：拆分为不同 code
P2 两个 saveStatusLog 实现不一致 OrderServiceImpl vs PaymentServiceImpl 支付日志没有操作人名。
修：抽公共组件
P2 finishService 用当前计价规则重算，与下单预估可能差异大 第 331 行 用户投诉「和预估价差太多」。
修：结算用下单时的规则快照
P2 update(null, wrapper) 不递增 version startService / finishService / cancelOrder version 无法反映真实修改次数。
修：显式写 version=version+1
P2 Redis 令牌在事务提交前释放 grab() 的 finally 短窗口多次进 DB（已被 CAS 兜住）。
修：TransactionSynchronization.afterCompletion
